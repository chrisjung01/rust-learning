Structs, impl, Self and ::new()

Where a Dart class does one job, Rust splits it in two: the struct holds the data, the impl block holds the behaviour.

The win for today: you can write a struct with a constructor and methods, and for every method you can say which of &self, &mut self or self it needs, and why.

Why it matters for the mission: every tool you plan to build is made of structs. The CLI's parsed arguments (clap derives them onto a struct), a serde config, an axum request body, the types flutter_rust_bridge turns into Dart classes. Running example for this lesson: the Task type of a small todo CLI.

1. The struct: only data

Dart
class Task {
  final String title;
  bool done = false;

  Task(this.title);

  void complete() => done = true;
}
Rust
struct Task {
    title: String,
    done: bool,
}

impl Task {
    fn new(title: &str) -> Self {
        Self { title: title.to_string(), done: false }
    }

    fn complete(&mut self) {
        self.done = true;
    }
}

The Dart class bundles fields, constructor and methods in one block. In Rust the struct only lists fields and their types. Behaviour lives in a separate impl Task { … } block, and a type may have several of them (Book 5.3). That split pays off later: traits (session 9) are also implemented in their own impl Trait for Task blocks, so "the data" and "what the data can do" stay separate pieces of code.

Owned fields: String, not &str

Notice title: String. You could try title: &str, but the compiler stops you with error[E0106]: missing lifetime specifier. A reference in a struct means "this struct must not outlive the data it points to", and Rust needs lifetimes (session 11) to check that. The Book's advice for now: "we want each instance of this struct to own all of its data and for that data to be valid for as long as the entire struct is valid" (Book 5.1). That's where session 1 comes back: new accepts a borrowed &str (callers can pass a literal or a &String) and creates the owned String inside.

2. Creating a value: there are no constructors

This is the biggest surprise coming from Dart. Rust has no constructor feature at all. There is only one way to create a struct value: the struct literal, which names every field:

let t = Task { title: String::from("Write tests"), done: false };

Leave out a field and it doesn't compile. Rust has no default field values, no implicit null, and no half-initialised object. The guarantee: whenever you hold a Task, every field has a valid value.

So what is Task::new? An ordinary function that happens to live in the impl block and returns a struct literal. The Book: "These are often called new, but new isn't a special name and isn't built into the language" (Book 5.3). The Rust API Guidelines make it the convention: "Constructors are static (no self) inherent methods for the type that they construct" (C-CTOR).

Why build it this way? A Dart constructor is special: it runs with a half-built this, has initializer lists, late fields and the rules about when this may be used. Rust drops all of that. Building a value is just an expression, so a "constructor" can do anything a function can: validate input, return Option<Task> or Result<Task, E> (session 6), or return a different value entirely. That's the role Dart gives to factory constructors, and in Rust every constructor already works that way.

Several constructors = several names

Rust has no function overloading, so you can't have two news with different parameters. Instead, you give them names. That's close to Dart's named constructors:

Dart
Task(this.title);
Task.done(this.title) : done = true;

final t = Task.done('Ship');
Rust
fn new(title: &str) -> Self { … }
fn new_done(title: &str) -> Self { … }

let t = Task::new_done("Ship");

Usual names from the guidelines: new for the main one, with_… for variants with extra settings (Vec::with_capacity(10)), from_… for conversions. Types that have an obvious empty state also implement Default (we'll see that with traits in session 9).

Two shortcuts in struct literals

Field init shorthand: if a variable has the same name as a field, write it once:

fn new(title: String) -> Self {
    Self { title, done: false }   // instead of title: title
}

Struct update syntax ..other fills the remaining fields from another value. It looks like Dart's copyWith, but there's a catch: it moves, like an assignment (Book 5.1):

let a = Task::new("Write tests");
let b = Task { done: true, ..a };   // a.title (a String) moves into b
println!("{}", a.title);            // error[E0382]: borrow of moved value: `a.title`

If only Copy fields (like bool, u32) are taken over, a stays usable. That's the same move rule as in session 1, applied to fields one by one.

3. impl and Self

Inside impl Task, Self (capital S) is an alias for the type: "Within an impl block, the type Self is an alias for the type that the impl block is for" (Book 5.3). -> Self and Self { … } mean exactly -> Task and Task { … }. You use it so the code doesn't repeat the type name, and later, with generics (impl<T> Stack<T>), it saves you from writing out long types.

Associated functions vs. methods

Every fn in an impl block is an associated function. If its first parameter is some form of self, it's also a method:

First parameterCallDart
associated functionnoneTask::new("x")static method / constructor
methodself, &self, &mut selftask.complete()instance method

:: means "something inside this namespace" (type, module); . means "call on this value". Methods can be called with :: too: Task::complete(&mut task) is the same as task.complete(). That shows what a method really is: a function whose first parameter is the value.

4. The three receivers

This is the part with no counterpart in Dart, and it ties straight into ownership. In Dart, this is always a reference to a mutable object. In Rust, every method declares how it gets access to self, and the three options are exactly the three kinds of access from session 1:

ReceiverShort forMethod may…Caller afterwards
&selfself: &Selfreadvalue unchanged, still usable
&mut selfself: &mut Selfread and changevalue changed, still usable; caller needs let mut
selfself: Selfanything, takes ownershipvalue is moved, gone

"&self is actually short for self: &Self" (Book 5.3).

impl Task {
    fn is_done(&self) -> bool { self.done }          // only reads
    fn complete(&mut self) { self.done = true; }        // changes
    fn into_title(self) -> String { self.title }        // consumes, hands out the String
}

let mut t = Task::new("Write tests");
t.complete();                  // needs `let mut t`
assert!(t.is_done());
let title = t.into_title();    // t is moved here
// t.is_done();                // error[E0382]: borrow of moved value: `t`

The rule of thumb: take the weakest access that works. &self by default, &mut self if the method changes fields, self only if the method turns the value into something else or uses it up. Typical self methods: into_… conversions (by naming convention, into_ consumes), builder methods, finish()/build(). Why into_title needs self: it gives away the owned String without cloning. With &self it could only return &str or a clone.

Why the signature says it: in Dart you have to read a method's body (or its docs) to know whether it changes the object. In Rust, &self in the signature is a promise checked by the compiler. You can see from the signature alone whether t.is_done() may change t, and the borrow rules from session 1 ensure nobody reads t while a &mut self method changes it.

Mutability belongs to the binding, not to the field

In Dart you mark individual fields final. Rust has no per-field mutability: "the entire instance must be mutable; Rust doesn't allow us to mark only certain fields as mutable" (Book 5.1). Whether a Task can change is decided by the person holding it (let vs let mut), not by the type. If you want "read-only from outside", you make fields private and offer no &mut self method that changes them, which leads to the next point.

Automatic referencing

You wrote t.complete(), not (&mut t).complete(). Rust adds &, &mut or * on its own so that the value fits the receiver: "Calling methods is one of the few places in Rust with this behavior" (Book 5.3). It never makes a value mutable for you, though: calling complete() on a plain let t is a compile error.

5. Getters and privacy, in short

A method may have the same name as a field: t.title() calls the method, t.title reads the field (Book 5.3). Rust generates no getters, unlike Dart's implicit ones. Usually you write one only when the field is private:

pub struct Task { title: String, done: bool }   // the type is public, the fields are not

impl Task {
    pub fn title(&self) -> &str { &self.title }   // read access, no clone
}

Fields are private by default, outside the module where the struct lives (Book 7.3). Code outside then cannot write a struct literal, and Task::new becomes the only way in. That's how a Rust type enforces invariants ("a title is never empty"). Modules are session 4. In today's exercises everything sits in one file, so privacy doesn't apply yet.

6. Two more struct forms

struct TaskId(u32);    // tuple struct: fields have no names, accessed as id.0
struct Done;           // unit-like struct: no fields at all

A tuple struct with one field is the newtype pattern: TaskId(u32) and UserId(u32) are different types, so mixing them up is a compile error, at zero runtime cost. Dart has no direct equivalent (extension types in Dart 3.3 are the closest). Unit-like structs matter later for traits (Book 5.1).

7. Check yourself

Answer from memory first, without scrolling up. The effort of recalling is what makes it stick.

1. impl Task { fn new(t: &str) -> Self { … } }: how do you call it?
new has no self parameter, so it's an associated function and is called through the type with ::. new is a plain name, not a keyword.
2. A method sets self.done = true. Which receiver does it need?
&mut self: it changes the value but the caller keeps it. self (lowercase) would also compile with mut self, but would consume the task. Self alone is a type, not a receiver.
3. fn into_title(self) -> String. After let s = t.into_title();, what about t?
A self receiver takes ownership. t moved into the method, any later use is E0382.
4. let t = Task::new("x"); t.complete(); with fn complete(&mut self). What happens?
Automatic referencing adds &mut, but you can only borrow mutably from a let mut binding. Mutability is a property of the binding.
5. Inside impl Task, what is Self?
Self is the type, self is the value. -> Self is exactly -> Task.
6. Why does almost every Rust type have a new function?
The language only knows struct literals. new is a convention (API Guidelines C-CTOR); Box::new allocates because of what Box does, not because of the name.
7. let b = Task { done: true, ..a };. Can you use a.title afterwards?
Struct update syntax moves non-Copy fields. ..a comes last, not first.
8. Why Task::new and Task::new_done instead of two news?
One name, one signature. A type may have several impl blocks, and new may take any parameters.

Predict the compiler

Which line fails, and with which error? Decide before you open it.

let t = Task::new("Ship it");
let done = t.is_done();
let title = t.into_title();
println!("{done} {title}");
t.complete();
Answer

The last line, with two errors at once: E0382 borrow of moved value: `t` (moved by into_title) and E0596 cannot borrow `t` as mutable, as it is not declared as mutable (no let mut). The compiler reports both. is_done before the move is fine: &self only borrows briefly.
